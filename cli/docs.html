Command line interface

pdfsuite

Run the PDF comparison engine headlessly — generate PDFs from JSON payloads, check them against golden references, and get a pass/fail exit code plus a visual report. Built to be driven from a shell script, Python, or a Jenkins job.

The only requirement on the caller is that Node 20+ is installed. Everything else is flags, files, and exit codes — so it is agnostic to whatever language drives it.

📤
generate POSTs each JSON payload to your render API and saves the returned PDFs, with retries, a heartbeat, and a manifest.
🔍
compare Runs every pair through the comparison engine and writes HTML, JSON, CSV and JUnit reports — then exits 0 or 1.
Same engine as the app The CLI does not reimplement the comparison — it imports the React app's own services and swaps the browser canvas for a Node one underneath. A verdict from the CLI is the verdict the app would show for the same pair.

How it works

Two commands, run in sequence. The first fills a directory with candidate PDFs; the second checks that directory against your goldens.

Where things live

cli/ ├── pdfsuite.config.json ← API url, headers, timeouts ├── fixtures/ │ ├── payloads/ ← example JSON inputs │ ├── golden/ ← reference PDFs to compare against │ └── pairs.json ← which candidate maps to which golden ├── mock-api/server.js ← stand-in for your real render API ├── dist/index.js ← the built CLI you run └── .work/ ← generated PDFs + reports (gitignored)

Setup

  1. Install and build

    From the repository root. This is separate from the React app's dependencies — installing here does not touch the app.

    bash
    $ cd cli $ npm install $ npm run build dist/index.js 951.2kb Done in 130ms $ npm link added 1 package

    npm link registers pdfsuite as a global command pointing at this checkout, so rebuilds take effect immediately with no re-linking. Prefer not to install anything globally? Every pdfsuite … on this page also works as node dist/index.js ….

  2. Check it works

    Run pdfsuite with no arguments and it tells you what it can do — the commands, a typical run, and what each exit code means.

    bash
    $ pdfsuite Usage: pdfsuite [options] [command] Generate PDFs from JSON payloads and check them against golden references. Commands: generate [options] POST each JSON payload to the render API and save the returned PDFs compare [options] Compare candidate PDFs against golden references and write reports pairs [options] Resolve and print the pairing table without comparing anything Typical run # 1. fill a directory with candidate PDFs pdfsuite generate --payloads ./payloads --out ./candidates # 2. check them against the goldens, write reports pdfsuite compare --reference ./golden --candidate ./candidates --pairs ./pairs.json --report ./reports Exit codes 0 every pair passed 1 a pair breached its thresholds — the PDFs changed 2 tool error — bad args, API unreachable, unmatched pair, nothing to compare Run `pdfsuite <command> --help` for the full flag list of any command.
  3. Start the mock render API

    In a second terminal. It serves the sample PDFs bundled with the app, so you can exercise the whole flow before pointing at a real backend.

    bash — terminal 2
    $ npm run mock-api Mock render API listening on http://localhost:4000 POST /render serving samples from ../public/samples GET /health
Check the API curl http://localhost:4000/health should return {"status":"ok", …}. If it reports degraded, the sample PDFs are missing from public/samples/.
Windows / PowerShell Every command on this page is written on a single line, so it pastes and runs the same in PowerShell, cmd and bash. Beware of multi-line examples elsewhere that end lines with \ — that continuation character is bash-only, and in PowerShell you would need a backtick instead. Use the short flags (-r -c -P -o) to keep long commands readable on one line.

Full walkthrough

Three commands end to end, using the bundled fixtures. No --api flag is needed — the URL comes from the config file.

This is the expected result The fixtures fail on purpose. invoice-standard is generated from a different template than its golden, so it must fail; invoice-identical uses the same template, so it must pass. A test set where everything passes would stay green even if the comparison logic were deleted.

Open .work/reports/report.html in a browser to see the annotated pages, the pixel-diff heatmap, and every change listed per page.

generate

Reads every *.json file in --payloads, POSTs each one to the render API, and writes <name>.pdf into --out.

Filename convention The payload's filename stem carries through the whole pipeline: acme-invoice.json → acme-invoice.pdf → referenced as "candidate": "acme-invoice.pdf" in pairs.json. Choose names that are stable and meaningful — they end up in the report and key your CI history.

The payload's contents are entirely yours. The CLI reads the file, checks it parses as JSON, and POSTs the bytes verbatim. It never inspects or requires any particular field — send whatever your render API expects.

Payload discovery is not recursive: only files directly inside --payloads are picked up, and only those ending in .json.

Adapting to your real API

Two settings usually cover it. If your API returns {"data":{"document":{"content":"…"}}} instead of {"pdfBase64":"…"}:

pdfsuite.config.json
{ "api": { "url": "https://render.internal.example.com/v1/documents", "responsePath": "data.document.content" } }

If the path is wrong, the error tells you what the response actually contained — Response has no string at "data.nope". Keys: documentId, template, generatedAt, pdfBase64.

The manifest

Every run writes <out>/manifest.json recording, per document: the payload name and its sha256, HTTP status, duration, attempts, output size and sha256. It is what lets you diagnose a CI failure without re-running a slow API.

compare

Runs every resolved pair through the engine — text extraction, word-level diff, text-position matching, and a pixel diff — then writes reports and sets the exit code.

What makes a page fail

A page passes when it clears all three thresholds. Any breach is named explicitly in the output and in the JUnit failure message, so you never have to guess which metric moved.

Content matchShare of text identical between the two pages. Must be ≥ the threshold. Catches wording changes.
Pixels differentShare of pixels that differ visually. Must be ≤ the threshold. Catches colour, spacing and graphics changes with no text delta.
Max offsetLargest distance a shared text run moved, in inches. Must be ≤ the threshold. Catches layout drift.

A page present on only one side is always a failure — it means a page was added or dropped.

pairs.json

Explicit mapping of which candidate is measured against which golden. This is the contract between the two commands.

fixtures/pairs.json
{ "defaults": { "contentPct": 99, "pixelPct": 2, "offsetIn": 0.03 }, "pairs": [ { "id": "invoice-standard", "name": "Invoice · standard layout", "reference": "invoice-original.pdf", // under --reference "candidate": "invoice-standard.pdf", // under --candidate "thresholds": { "pixelPct": 5 }, // overrides defaults "skipPages": [6] // 1-based, excluded from verdict } ] }
Field
id requiredStable identifier. Becomes the JUnit <testsuite name>, the report anchor, and the asset folder. Do not rename it casually — CI keys test history off the suite name, so a changed id reads as “old test deleted, new test added” and discards that pair's trend graph.
nameHuman label shown in reports. Defaults to id.
reference requiredPath relative to --reference. Never absolute.
candidate requiredPath relative to --candidate. Never absolute.
thresholdsPer-pair overrides merged over defaults. Use for documents that are legitimately noisier.
skipPages1-based page numbers excluded from the verdict — generated dates, barcodes, anything that always differs.
Unmatched entries are fatal If a reference or candidate file does not exist, the run stops with exit 2 — it is not a warning. A missing candidate means generation silently dropped a document, which is exactly the regression worth catching. Reporting on the remaining pairs would hide it.

Paths are always relative to the two directory flags — never absolute, never relative to the pairs file, never cwd-dependent. That keeps one pairs.json working unchanged on a laptop and on a CI agent with a different workspace path.

CLI flags

What to process now

Varies with every invocation, so it belongs on the command line.

  • --payloads / --out
  • --reference / --candidate
  • --pairs / --report

Discovery

The file is found by walking up from the working directory — the way git and eslint do — so commands work from anywhere inside the project. The resolved path prints at the top of every run, so which settings applied is never a mystery.

auto-discovered --config ./other.json --no-config

Secrets

Never commit a token. Any string value expands ${ENV_VAR} from the environment, so the committed file references a secret that only exists on the CI agent.

pdfsuite.config.json
"headers": { "Authorization": "Bearer ${RENDER_API_TOKEN}", "X-Client": "pdfsuite-cli" }
A missing variable is a hard error Not an empty string. Sending Authorization: Bearer would produce a 401 from the API and a confusing hunt far from the real cause — so the run stops immediately, naming the exact config path that referenced it.

Precedence

An explicitly passed flag always wins, then the config file, then the built-in default. -H headers merge over the config's headers object, so a one-off override does not require editing the committed file.

CLI flag› config file› built-in default

Unknown top-level keys are rejected. A typo like "comapre" fails loudly rather than being silently ignored while the CLI quietly uses a default you did not intend.

Working with a slow API

Real PDF rendering commonly takes 20–40 seconds per document. The defaults assume that, and four things follow — each one the difference between a run that works and one that fails for reasons unrelated to your PDFs.

Generous timeout

Default 120000 (2 minutes) against a 40s API. A timeout that fires on a healthy-but-slow response turns a working pipeline red. There is no penalty for a generous timeout, only for a tight one — raise it further if your p99 is worse.

Timeouts are not retried

If a request blew past an already-generous timeout, the retry almost certainly will too — you have tripled the wall clock and still failed. Measured on the mock API, 8 documents timing out:

Wall timeWasted attempts
default5.3s0
--retry-on-timeout16.8s16

5xx responses and network faults are retried, because a retry can actually fix those.

Heartbeat

With 40s calls a run is otherwise silent for minutes, which reads as a hang — and CI runners routinely kill jobs that produce no output for N minutes. The heartbeat keeps a long job alive and legible:

generate — 30s API, concurrency 3
… 3 in flight · longest acme-invoice-feb 10.0s · 0/8 done … 3 in flight · longest acme-invoice-feb 20.0s · 0/8 done … 3 in flight · longest acme-invoice-feb 30.0s · 0/8 done ✓ acme-invoice-feb — 12.3KB in 30.1s ✓ globex-invoice-feb — 12.3KB in 30.1s ✓ acme-invoice-jan — 13.5KB in 30.1s … 3 in flight · longest globex-invoice-jan 10.0s · 3/8 done · ETA ~60.1s 8/8 generated in 1m30s 8 API call(s) · average 30.0s · slowest 30.1s

The ETA is projected from completed API calls only, so it is absent on the first wave and accurate afterwards.

Resuming a partial run

When each call costs 40s, re-running a 200-document batch to recover 3 failures is not viable. --skip-existing reuses what is already on disk and fetches only what is missing.

bash
$ pdfsuite generate -p ./payloads -o ./candidates --skip-existing ⏭ acme-invoice-feb — exists, skipped ⏭ globex-invoice-feb — exists, skipped ✓ acme-invoice-jan — 13.5KB in 30.1s ✓ tyrell-statement — 8.0KB in 30.1s 8/8 generated in 30.2s (6 reused from disk) 2 API call(s) · average 30.1s · slowest 30.1s

Reused files are excluded from the timing statistics, so average and slowest still describe real API calls.

Concurrency caveat If the API is slow because rendering is CPU-bound, raising --concurrency may just queue requests server-side and push them all past the timeout at once. Start at 4 and raise it only if you have measured that it helps.

Exit codes

The primary contract with CI. Separating “the PDFs regressed” from “the job is broken” is what lets a pipeline react correctly to each.

0
Passed
Every pair cleared its thresholds.
1
Comparison failed
At least one pair breached a threshold. The documents changed — investigate the report.
2
Tool error
Bad arguments, unreachable API, unreadable PDF, unmatched pair, zero pairs resolved. The job is broken, not the PDFs.
Zero pairs is an error, never a pass A run that compares nothing and exits 0 is the exact failure this tool exists to prevent — a green pipeline that is silently checking nothing.

Use --fail-on none when you want the reports but always a zero exit, e.g. on a branch where failures should not block the build.

Reports

Four outputs, written to --report. Choose with --format.

🖼️
report.html The full visual report — annotated A/B pages, the pixel-diff heatmap with layout/text colour coding, before→after labels, and a per-page change list. Built from the app's own exporters, so it is the same report the app produces. Print → Save as PDF to share.
⚙️
junit.xml One <testsuite> per pair, one <testcase> per page. Jenkins, GitLab and GitHub Actions render this natively — per-page pass/fail history and “what newly broke” for free.
🧾
report.json Per-pair and per-page metrics, verdicts, and the specific thresholds breached. For scripts that need to act on the detail.
📊
report.csv One row per pair × page. For spreadsheets and quick trend charts.

Use in CI

The API url and headers come from the committed config; only the token is injected from credentials, and only paths are passed as flags.

Jenkinsfile
stage('PDF regression') { environment { RENDER_API_TOKEN = credentials('render-api-token') } steps { sh 'cd cli && npm ci && npm run build' sh 'cd cli && node dist/index.js generate -p $WORKSPACE/payloads -o $WORKSPACE/.work/candidates' sh 'cd cli && node dist/index.js compare -r $WORKSPACE/golden -c $WORKSPACE/.work/candidates -P $WORKSPACE/pairs.json -o $WORKSPACE/.work/reports' } post { always { junit '.work/reports/junit.xml' archiveArtifacts artifacts: '.work/reports/report.html' } } }

From Python

python
import subprocess r = subprocess.run([ "node", "cli/dist/index.js", "compare", "--reference", "golden", "--candidate", "candidates", "--pairs", "pairs.json", "--report", "reports", ], check=False) # 0 = all passed · 1 = PDFs regressed · 2 = tool/config error if r.returncode == 2: raise RuntimeError("pdfsuite failed to run")

Point a different environment at a different backend with one flag — --config ./config/staging.json — rather than editing the job.

Troubleshooting

SymptomCause & fix
No render API URL Neither api.url in the config nor --api was set. The run stops before making any request.
No .json payloads in … The directory is empty, or the payloads sit in subdirectories — discovery is not recursive. Use one flat directory per run.
Response has no string at "…" Wrong --response-path. The error lists the keys the API actually returned — set api.responsePath to match.
… references ${VAR}, which is not set The config references an environment variable that is missing. Export it, or replace the reference with a literal.
N pair(s) could not be resolved A file named in pairs.json does not exist. Run pdfsuite pairs to see exactly which entry is broken.
Timed out after 2m00s The API exceeded the timeout. Raise api.timeout; add --retry-on-timeout only if timeouts are genuinely transient.
Everything fails after moving to a new machine Font availability. pdf.js substitutes missing fonts, which shifts pixels — goldens blessed on one machine can fail on an agent with a different font set. Pin comparison runs to a container image with a known font set.
Noisy pdf.js font warnings Filtered by default; rendering is unaffected. Pass --verbose to see them.
