Python package

pdfsuitepy

The same PDF regression pipeline as the Node CLI, installable with pip and usable as a Python library. Generate candidate PDFs from JSON payloads, check them against golden references, and get typed results plus a pass/fail exit code.

native python generate Calls your render API for each payload and saves the PDFs. Stdlib only — no Node, no third-party packages.
delegates to node compare Runs the same engine the React app runs, so a verdict here is the verdict the app would show for the same pair.
Zero runtime dependencies pyproject.toml declares none. This drops into arbitrary CI environments and existing Python projects, where an added dependency is a version conflict waiting to happen. urllib covers everything generate needs.

The two halves

The commands are implemented differently because they are not equally portable.

Why generate was ported

It contains no comparison logic — it is HTTP, base64 and file writes. Porting carries zero fidelity risk, and it means a Python-only workflow can fetch candidates with no JS runtime present.

Why compare was not

Every number it produces comes from pdf.js rendering. A Python port on PyMuPDF or pypdfium2 would rasterize differently — different anti-aliasing, font hinting and subpixel positioning — so pixel ratios, content-match percentages and offsets would all drift.

What drift would cost Thresholds tuned in the app would be wrong here. Goldens blessed with one tool would fail with the other. The app would show PASS while Python showed FAIL for the same pair, and nobody could say which was right. Delegating keeps one source of truth.

Which engine was found is never a mystery — pdfsuitepy --version prints it.

Setup

  1. Build the Node engine

    Needed by compare. Skip if you only use generate.

    bash
    $ cd cli $ npm install $ npm run build
  2. Install the Python package
    bash
    $ cd cli-py $ pip install -e .
  3. Confirm it found the engine
    bash
    $ pdfsuitepy --version pdfsuitepy 1.0.0 engine: node v20.12.2 · C:\…\cli\dist\index.js

    The bundle is located by walking up from the package and from the working directory, so a source checkout needs no configuration.

Walkthrough

Against the bundled mock API (cd cli && npm run mock-api). No --api flag needed — the URL comes from the shared config file.

compare — delegates, streams live

bash
$ pdfsuitepy compare -r ./golden -c ./candidates -P ./pairs.json -o ./reports 3 pair(s) resolved · 0 problem(s) [1/3] invoice-standard … FAIL · 6 pages, 4 failing · 1277ms [2/3] invoice-identical … PASS · 6 pages · 1279ms [3/3] statement-summary … PASS · 2 pages · 477ms wrote reports/report.json (5 KB) wrote reports/junit.xml (3 KB) 2/3 pair(s) passed ✗ invoice-standard — page 5: content 83.91% < 99%, pixels 9.92% > 2%, offset 2.181" > 0.03" $ echo $? 1
Output is streamed, not captured The subprocess writes straight through. Buffering it would make a long run look hung — the exact CI-watchdog problem the heartbeat exists to avoid.

Library API

The main reason to use this instead of writing subprocess.run yourself: results come back as dataclasses.

python
from pdfsuite import compare, generate generate( payloads="./payloads", out="./candidates", api="https://render.example.com/v1/documents", quiet=True, ) result = compare( reference="./golden", candidate="./candidates", pairs="./pairs.json", report="./reports", quiet=True, ) if not result.passed: for pair in result.failures: worst = pair.worst_page print(pair.id, "page", worst.page, worst.breaches)
output
invoice-standard page 5 ['content 83.91% < 99%', 'pixels 9.92% > 2%', 'offset 2.181" > 0.03"']

quiet=True suppresses all progress output, for when you want the returned object rather than a running log.

In pytest

No plugin ships yet, but the library API is already enough to drive a test suite.

test_pdfs.py
import pytest from pdfsuite import compare @pytest.fixture(scope="session") def report(tmp_path_factory): return compare( reference="golden", candidate="candidates", pairs="pairs.json", report=str(tmp_path_factory.mktemp("reports")), quiet=True, ) @pytest.mark.parametrize("pair_id", ["invoice-standard", "statement-summary"]) def test_pair_matches_golden(report, pair_id): pair = next(p for p in report.pairs if p.id == pair_id) assert pair.passed, pair.worst_page.breaches

One test per pair, failures rendered by pytest, -k filtering for free. Comparing once in a session fixture keeps the cost to a single engine run.

Configuration

Reads the same pdfsuite.config.json the Node CLI does — same discovery (walking up from the working directory), same ${ENV_VAR} expansion, same validation, same precedence. Configuration does not fork between implementations, so switching one for the other cannot silently change behaviour. pairs.json is shared unchanged too.

pdfsuite.config.json
{ "api": { "url": "https://render.example.com/v1/documents", "auth": { "type": "bearer", "token": "${API_TOKEN}" }, "responseMode": "binary" }, "paths": { "payloads": "./payloads", "out": "./candidates" } }

Precedence: explicit flag › config file › built-in default. Auth schemes (bearer, basic, header, query) and response modes (json, binary, base64) are all supported natively by the Python generate.

Unknown keys are rejected at every level A typo like api.timout fails loudly, listing the keys that are valid there — rather than being silently ignored while a default you did not intend takes effect.

Exit codes

Identical to the Node CLI, so a pipeline can switch implementations without changing how it reads a result.

0
Passed
Every pair cleared its thresholds.
1
Comparison failed
A pair breached a threshold. The documents changed.
2
Tool error
Bad args, unreachable API, unmatched pair, nothing to compare. The job is broken, not the PDFs.

Running pdfsuitepy bare prints help and exits 0 — asking what a tool does is not an error.

Verification

All measured against the bundled mock API.

Byte-identical output

PDFs from pdfsuitepy generate sha256-compared against both the Node CLI's output and the original sample files, across every response shape:

cross-check
json 3 pdfs byte-identical to source binary 3 pdfs byte-identical to source base64 3 pdfs byte-identical to source nested 3 pdfs byte-identical to source -> all modes lossless

Identical comparison metrics

Because compare is the same engine rather than a reimplementation, it reproduces the Node CLI's numbers exactly — 95.82% / 92.94% / 0.264″ / 83.91% / 9.92% / 2.181″.

Manifest parity

Field-by-field diff against a Node-produced manifest: no differing entry fields, and only the additive producedBy key at the top level, so either tool can read the other's output.

Credential redaction

api_key=*** in both the log and the manifest, byte-for-byte matching Node. Grepping the artifacts for the real key finds nothing.

16/16 parity checks

Four auth schemes, four response modes, compare/pairs delegation, --fail-on none, and five misconfiguration cases — all producing the same exit codes as the Node CLI.

Limitations

  • compare requires Node ≥ 20. Checked up front with an actionable error rather than a cryptic failure from the bundle. generate needs nothing but Python.
  • The Node bundle must be built (cd cli && npm run build) before compare works.
  • Font availability still applies. pdf.js substitutes missing fonts, which shifts pixels — goldens blessed on one machine can fail on an agent with a different font set. Unchanged from the Node CLI; pin comparison runs to a container image with a known font set.
  • No pytest plugin yet. The library API supports the pattern above, but a first-class fixture with per-pair test IDs is not built.
