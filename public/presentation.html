The problem

“Looks fine to me”

Templates get edited. Documents get regenerated. Somebody eyeballs a few pages and signs off — and a font change on page 4 ships to customers.

Manual review doesn't scale

A 6-page invoice has hundreds of text runs. Checking every one by eye, across every template revision, is not work anyone does reliably twice.

“Different” isn't actionable

Knowing 6% of pixels moved doesn't tell you what to fix. Was a word edited? A font swapped? A block nudged? Each has a different fix.

Sometimes there's no reference

New pages have nothing to compare against — only a spec saying what should be on them, and where.

What's in the box

Four workspaces

One app, four jobs. Everything runs locally in the browser — no document ever leaves the machine.

How it works

The comparison pipeline

Every page goes through the same five stages. Both documents are normalised into one coordinate space first, so every measurement is directly comparable.

The core idea

Three kinds of difference

Every difference lands in exactly one category. Which one it is tells you what to go and fix.

Content

The words changed

A line, heading or paragraph was edited. Reported at word granularity — "approach" → "strategy", not the whole sentence.

Style

Same words, different type

Font family, size, weight or slant changed while the text stayed identical. Helvetica → Helvetica-Bold.

Layout

Same words and type, moved

The element is unchanged but sits somewhere else. Reported as the correction to apply — increase y by 0.250in.

Precedence, when one element qualifies for more than one content > style > layout. The higher category explains the lower one — editing a word changes its width, which shifts everything after it. Reporting the consequence instead of the cause sends you to the wrong place, and reporting both double-counts one change.
Why this is harder than it looks

One word, bolded

PDF viewers start a new text run wherever the font changes. Restyle a single word and the whole line is re-cut — so a naïve comparison sees a deleted sentence and three new ones.

what the PDF actually contains
side A — 1 run "we took a different approach to this problem" side B — 3 runs "we took a different " "approach" ← bold " to this problem"
classification
naïve — compares runs as strings removed "we took a different approach…" added "we took a different" added "approach" added "to this problem" → 3 content changes this tool — re-cuts into words styled "approach" Helvetica → Helvetica-Bold → 1 style change

The give-away: the content-match score already read 100% — the text never changed. Leftover runs are re-cut into words and diffed word by word, so the change list and the score agree.

When there's no reference

Test against a spec

Describe what a page should contain in JSON — text, images, tables, paragraph spacing, positioned in inches — and check a generated PDF against it.

spec.json
{ "type": "image", "id": "brand-logo", "top": 0.55, "left": 6.4, "width": 1.6, "height": 0.6, "anchor": { "text": "MONTHLY STATEMENT", "position": "right" } }

Anchors beat coordinates

An image has no text to search for, so without an anchor it can only be found by proximity — and latches onto a neighbour when the layout reflows. An anchor ties it to a label the page actually shows.

Found, then judged

Position is still asserted. A correct anchor with a wrong position reports Top: FAIL and tells you by how much — instead of an unhelpful not-found.

Output

Five ways to read the result

HTML report

Annotated pages, the pixel-diff heatmap colour-coded by category, before→after labels, and a per-page change list. Print to PDF to share.

JUnit XML

One testsuite per document, one testcase per page. Jenkins and GitLab render it natively — per-page history and “what newly broke” for free.

JSON & CSV

Every metric, verdict and breached threshold for scripts; one row per document × page for spreadsheets.

Markdown fix-list — written for an AI agent, not a person

Every finding paired with the change needed in the source template. Positions in inches and font sizes in points, so values map straight onto AEM Forms XDP attributes. Deltas are given as the correction to apply, never the drift observed. Cascading shifts are grouped by shared delta — a deleted table row reads as one finding instead of thirty.

Automation

Same engine, from the command line

The CLI imports the app's own comparison services and swaps the browser canvas for a Node one. It doesn't reimplement anything — so a CLI verdict is the verdict the app would show.

bash
$ pdfsuite generate --payloads ./payloads --out ./candidates ✓ invoice-standard — 12.3KB in 45ms … 3 in flight · longest acme-invoice 30.0s · 3/8 done · ETA ~60s $ pdfsuite compare -r ./golden -c ./candidates -P ./pairs.json -o ./reports [1/3] invoice-standard … FAIL · 6 pages, 4 failing [2/3] invoice-identical … PASS · 6 pages wrote reports/report.html · report.json · junit.xml · remediation.md $ echo $? 1 0 = passed · 1 = PDFs regressed · 2 = the job is broken

Separating exit 1 from 2 is what lets a pipeline tell “the documents changed” from “the build is broken”.

Libraries · 1 of 2

The three that do the work

Everything the tool concludes traces back to these. The rest is plumbing.

pdfjs-dist Mozilla · 4.7
Reads the PDF. Rasterises each page to a canvas at ~144 DPI, and extracts every text run with its transform matrix — position, font size — plus the font it was drawn with. Font names come from its resolved font objects, which is how bold / italic / family changes are detected at all. It's also the source of the run-splitting quirk on the previous slide.
pixelmatch Mapbox · 5.3
Compares the two images. A perceptual pixel diff with an adjustable threshold and anti-aliasing detection, returning a changed-pixel count and a heatmap. This is what catches differences with no text delta at all — a recoloured bar, a shifted rule, a redrawn chart.
diff jsdiff · 5.2
Compares the text. Used twice: diffWords scores the page-level content match, and diffArrays produces the word-level change list — multiple edits on one line stay separate findings instead of merging into one replaced sentence.
Libraries · 2 of 2

The supporting stack

React + TypeScript 18.3 · 5.6
The four workspaces. TypeScript matters more than usual here: the engine's types are shared by the UI, the CLI and the report writers, so a change to the comparison model can't quietly break one of them.
Zustand 4.5
Application state — loaded documents, the per-page comparison cache, thresholds, view mode. Chosen over Context so a single page's result landing doesn't re-render the whole tree.
Vite 5.4
Dev server and production build.
@napi-rs/canvas 0.1
Makes the browser engine run headlessly. Provides canvas, Image and ImageData to Node so the app's own rendering code works unchanged in the CLI. Ships prebuilt binaries — no Cairo, no build toolchain on the agent.
esbuild 0.24
Bundles the CLI, and hosts the two shims that let browser code run under Node — resolving Vite's ?url imports and pointing pdf.js at its Node build.
Commander · Express 12 · 4.21
Command parsing and help output; and a small mock render API so the whole generate→compare loop can be exercised locally without a real backend.
Architecture

One engine, two front ends

The comparison logic exists once. The browser app and the CLI are both thin layers over it — which is why they can never disagree about the same pair of documents.

How we know it's right

Classification is pinned by tests

Purpose-built PDF pairs, each isolating one kind of change, assert which category it lands in — and that no single element ever lands in two.
